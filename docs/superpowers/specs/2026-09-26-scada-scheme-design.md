# Мнемосхема котельной («Схема») — дизайн

Дата: 2026-09-26 · Ветка: `feature/scada-scheme`

## 1. Цель

Новая страница веб-интерфейса — **главный пульт** в стиле SCADA: вся котельная на одной
иллюстрированной схеме, состояние оборудования видно прямо на рисунке, управление — кликом по
элементу. Страницы «Отопление» и «Водоснабжение» остаются для редких детальных настроек
(расписания, графики кривых ПЗА, анти-легионелла) — окна схемы ссылаются на них.

Критерии успеха:
- по одному взгляду понятно: что работает, что стоит, какие температуры и давление, есть ли аварии;
- любой параметр, который меняют в обычной жизни, меняется со схемы в 2 клика;
- схема живая (обновление без перезагрузки), работает на компьютере, планшете и телефоне,
  в светлой и тёмной теме.

Вне рамок (YAGNI): тренды на схеме, комнатные датчики поштучно, редактор расписаний и кривых в окнах,
мобильное приложение, редактор схемы.

## 2. Решения

| Вопрос | Решение |
|---|---|
| Роль страницы | Главный пульт; детальные настройки остаются на существующих страницах |
| Стиль | Иллюстративный (как `ForSite.png`): узнаваемые котёл, радиаторы, бойлер, петли пола; трубы красные/синие |
| Реализация | Inline SVG из React-компонентов (вариант A). Без растровых картинок и без диаграммных библиотек |
| Экраны | Две раскладки одной топологии: горизонтальная (≥ 900 px) и вертикальная (телефон) |
| Запись | Изменения копятся в окне, уходят одним `PUT /settings` по «Применить» |

## 3. Состав схемы

Топология по схеме пользователя: котёл слева → гидрострелка + коллектор в центре → К1 радиаторы
сверху, К2 тёплый пол снизу, К3 бойлер ГВС справа; правее бойлера — ГВС к кранам с
насосом рециркуляции, внизу ввод ХВС; кран автоподпитки под гидрострелкой.

Общие правила отображения:
- подача красная, обратка синяя; цвет трубы интерполируется по фактической температуре
  (≤ 25 °C синий → ≥ 70 °C красный); по трубам с работающим насосом — анимация потока
  (отключается при `prefers-reduced-motion`);
- табло значения у каждого датчика; значение старше `sensor_stale_minutes` → серое «—»;
- нет heartbeat дольше `heartbeat_timeout_seconds` → схема приглушается, плашка
  «Нет связи с контроллером»; управление доступно (значения сохранятся в config_kv
  и дойдут при переподключении — существующий механизм resync);
- права: viewer — только просмотр; operator — всё, кроме защитных пределов; admin — всё.
  Недоступные контролы видны, но заблокированы (зеркало `setting_rules.py`).

| Элемент | Показывает | Окно управления |
|---|---|---|
| Котёл | режим (авто/ручной), реле питания, подача/обратка, цель автомата; мигание при `overtemp` / `boiler_sensor_lost` | авто/ручной, питание (в ручном), `heating_boiler_temp`; `heating_boiler_max_temp` — admin |
| Гидрострелка + коллектор | манометр давления контура, норма min–max | = окно автоподпитки |
| Кран автоподпитки | закрыт / открывается (`af_open`) / закрывается (`af_close`) / **заблокирован** (`autofill_fault`) | `heating_autofill_enabled`; `heating_pressure_min/max` — admin; «Сбросить блокировку» (`autofill_reset`) |
| К1 Радиаторы | насос (вращение), 3-ходовой клапан (↑/↓ во время импульса, реле 9/10), подача/обратка, цель (`rad_target`), значки «Ночь» (`schedule_rad`) и «Приоритет ГВС» | насос, ПЗА, кривая 1–5, ручная уставка, откл. при нагреве БКН; → «Отопление» (расписание) |
| К2 Тёплый пол | как К1 (`floor_*`, реле 11/12) | как К1 |
| К3 Бойлер ГВС | T бака и цель (`ihb_target`), насос загрузки, обратка змеевика, ТЭН, значок анти-легионеллы (`alm_active`) | авто БКН, насос (в ручном), уставка, ТЭН авто/вкл, задержка ТЭН; → «Водоснабжение» (анти-легионелла) |
| ХВС | насос, T ввода, давление | насос вкл/выкл |
| ГВС к кранам | T выхода, насос рециркуляции | рециркуляция вкл/выкл |
| Любой датчик | значение, «обновлено N с назад» | ссылка на графики |

Верхняя полоса: улица, средняя по дому, котельная; связь с контроллером; число
несинхронизированных команд + «Повторить» (`POST /settings/retry-unsynced`).

Табло сигнализации: лампы warning/critical контроллера; активные аварии текстом
(давление вне нормы, перегрев, потеря датчика котла, блокировка подпитки, нет связи);
3 последних события + ссылка на «Журнал».

## 4. Раскладки и окно управления

- **Горизонтальная** (≥ 900 px): SVG viewBox 1000×560, табло сигнализации справа внизу.
- **Вертикальная** (< 900 px): viewBox 360×640, котёл | коллектор | бойлер в один ряд,
  радиаторы над ним, пол под ним; ХВС/ГВС/подпитка/сигнализация — строка внизу,
  сигнализация разворачивается по тапу.
- Обе раскладки используют одни и те же компоненты элементов; различаются только координаты
  (`layouts.ts`). SVG масштабируется по ширине контейнера.
- **Окно управления**: на компьютере — модальное окно по центру, на телефоне — нижняя
  выезжающая панель. Шапка — текущее состояние элемента; ниже контролы; внизу
  «Отмена / Применить». Отправляются только изменённые ключи. После отправки у каждого
  изменённого параметра: ⏳ (ждём ack) → ✓ (подтверждён) или ⚠ «не синхронизировано»
  (из статуса шлюза). Ошибки валидации/прав (422/403) показываются у поля.

## 5. Данные

### 5.1 `GET /api/v1/scheme/state` (новый, требует вход, любая роль)

```jsonc
{
  "generated_at": "2026-09-26T12:00:00Z",
  "values": {                       // по ролям элементов
    "boiler_supply":  {"value": 75.1, "ts": "…Z", "stale": false},
    "boiler_return":  {…}, "rad_supply": {…}, "rad_return": {…},
    "floor_supply": {…}, "floor_return": {…}, "tank": {…}, "coil_return": {…},
    "cold_water": {…}, "hot_water": {…},
    "heating_pressure": {…, "source": "sensor" | "heartbeat"},
    "water_pressure":   {…, "source": …},
    "outdoor": {…}, "indoor_avg": {…}, "boiler_room": {…}
  },
  "controller": {                   // из heartbeat boiler_unit (через шлюз)
    "online": true, "last_seen": "…Z", "relays": {"boiler": true, "rad_pump": true, …},
    "flags": {"warning": false, "critical": false, "overtemp": false,
              "boiler_sensor_lost": false, "autofill_fault": false,
              "alm_active": false, "schedule_rad": false, "schedule_floor": false,
              "ihb_heating": false, "autofill_active": false, "autofill_closing": false},
    "targets": {"boiler": 56.0, "rad": 54.0, "floor": 29.2, "ihb": 55.0}
  },
  "settings": {"heating_boiler_automode": "1", …},   // config_kv без секретов
  "sync": {"pending": ["heating_radiator_curve"], "unsynced": []},
  "alarms": [{"level": "ERROR", "code": "pressure_low", "text": "Давление 0.92 бар ниже нормы 1.0"}],
  "events": [{"ts": "…Z", "level": "INFO", "text": "…"}],
  "stale_minutes": 5
}
```

Привязки ролей (одно место — `app/services/scheme_service.py`):
- подача/обратка котла, К1, К2, К3 — точки монтажа из `heating_circuits` по `config_prefix`
  (`heating_boiler`, `heating_radiator`, `heating_floorheating`, `watersupply_ihb`), датчик через
  `MountPoint.temperature_sensor_id` (как дашборд);
- ХВС/ГВС — датчики `tswatersupply_c` / `tswatersupply_h`;
- давление — привязанный датчик `prs` (если есть), иначе `prs_heat` / `prs_water` из heartbeat;
- улица — `SensorRepository.get_outdoor_temp()`; дом — среднее свежих климатических датчиков (system 3)
  кроме уличного и неотапливаемых (константа `UNHEATED_SENSORS = {"clm_garage_th"}` рядом с привязками);
  котельная — датчик `clm_boiler_th`;
- реле — битовая маска `relays` по порядку `RelayChannel` прошивки.

Аварии формирует сервер (одна логика для всех клиентов): флаги heartbeat + давление вне
`heating_pressure_min/max` + перегрев + «нет связи».

### 5.2 Шлюз: списки ключей синхронизации

`GET /health` шлюза дополнительно отдаёт `sync: {device: {"pending": [...], "unsynced": [...]}}`
(сейчас только счётчики). Существующие поля не меняются.

### 5.3 Прошивка и эмулятор: мгновенный heartbeat

После обработки пачки команд контроллер сразу публикует heartbeat (плюс обычный раз в 30 с),
чтобы состояние реле на схеме обновлялось без 30-секундной задержки. То же в эмуляторе.

### 5.4 Обновление на клиенте

`useSchemeState`: загрузка при открытии; refetch на WS `sensor_update`/`settings_update`
(throttle 2 с) и по таймеру 10 с; пока в окне есть ⏳-параметры — таймер 2 с.

### 5.5 Запись

«Применить» → `PUT /api/v1/settings` (существующая валидация, роли, доставка).
«Сбросить блокировку» → `POST /api/v1/catalog/devices/boiler_unit/command {"autofill_reset":"1"}`
(admin). «Повторить» → `POST /api/v1/settings/retry-unsynced`. Новых путей записи нет.

```

frontend/src/scheme/SchemeCanvas.tsx       SVG: трубы + элементы по раскладке
frontend/src/scheme/elements/*.tsx         Boiler, Separator, Radiators, FloorLoops, Tank, Pump,
                                           MixingValve, FillValve, Gauge, ValueTag, Pipe, Tap

frontend/src/scheme/forms/*.tsx            BoilerForm, CircuitForm, TankForm, AutofillForm, PumpForm
```

Элементы — чистые компоненты (данные через props, без запросов). Цвета — через CSS-переменные,
зависящие от темы. Раскладка выбирается по ширине контейнера (`ResizeObserver`), не по UA.

## 7. Ошибки и крайние случаи

- шлюз недоступен → `controller.online=false`, `sync` пусто, плашка «Шлюз недоступен»;
- датчик не привязан/нет данных → табло «—», элемент не мигает;
- heartbeat без нужного поля (старая прошивка) → соответствующий значок скрыт;
- частичная ошибка «Применить» (422 по одному ключу) → ничего не сохраняется (API валидирует пачку
  целиком), ошибка у поля;
- выход из окна с несохранёнными изменениями → подтверждение.

## 8. Тестирование

- **backend**: `scheme_service` — привязки по контурам, fallback давления на heartbeat, stale,
  формирование аварий, отсутствие шлюза; эндпоинт — 401 без входа, секреты не отдаются;
  шлюз — списки pending/unsynced в `/health`.
- **frontend**: `pipeColor`; элементы рисуют состояния (вращение/стоп, заблокирован, stale,
  нет связи); `ControlDialog` отправляет только изменённые ключи, блокирует admin-поля для operator.
  (Vitest + Testing Library — добавляются как dev-зависимости, в проекте их пока нет.)
- **эмулятор/прошивка**: heartbeat после команды.
- **сквозная**: локальный стенд с эмулятором, Playwright-скриншоты обеих раскладок в светлой и
  тёмной теме; сценарии: выключить насос → насос остановился на схеме < 3 с; `leak 400` →
  блокировка подпитки на схеме и в сигнализации.
