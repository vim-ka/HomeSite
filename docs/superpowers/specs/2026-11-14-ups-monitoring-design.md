# Мониторинг ИБП: страница, графики, тревоги и СМС

Дата: 14.11.2026. Ветка `feature/ups-2026-11` — от `main` после слияния СМС (пользуется её очередью СМС).
Решения Andrey помечены **(владелец)**, мои — **(моё)**, их можно оспорить.

## Зачем

Дома несколько ИБП APC. Сейчас неизвестно, когда пропало электричество, сколько осталось батарее и не пора ли
менять аккумулятор. Нужно следить за «здоровьем всех ИБП» **(владелец)**: видеть их на отдельной странице, строить
график напряжения сети и получать СМС **(владелец)** о пропаже электричества, разряде и выходе напряжения за пределы.

Успех: пропал свет → через минуту СМС «Нет электричества: «Серверный» работает от батареи, заряд 95%, осталось
~40 мин», вернулся — «Электричество вернулось, не было 12 мин». На странице «ИБП» видно, какой ИБП что питает,
его заряд, нагрузку, напряжение и состояние батареи.

## Известное железо

- APC Back-UPS Pro 1200 и APC Back-UPS BE550G-RS (ES 550) **(владелец)**. У обоих порт данных — USB (разъём RJ45 на
  Pro и «RS485» на ES — это порт под кабель USB APC, а не сеть/RS485) **(моё, проверить при подключении)**.
- Есть ещё ИБП; всего удалённых (без компьютера рядом) — 3 **(владелец)**. Начинаем с котельной **(владелец)**:
  **APC Smart-UPS 750** (по виду серия SUA), от него питается **вся котельная** — котёл, насосы, контроллер
  **(владелец)**; в котельной только Wi-Fi, сетевого кабеля нет **(владелец)**. У Smart-UPS есть COM-порт (DB9) с
  текстовым протоколом APC «Smart», USB и слот под сетевую карту.
- Сейчас ИБП не подключены. Делаем сейчас, проверяем на имитации, на железе — после подключения **(владелец)**.
- Модель котельной по фото: светодиоды и две кнопки, без экрана → серия **SUA** (или старая SU), обе с протоколом
  «Smart» **(моё; у SMT/SMC есть экран и нет «Smart»)**. Артикул на наклейке сверить перед покупкой деталей.
- **Условие для СМС о свете:** роутер, точка Wi-Fi в котельной и хост с ВМ сейчас **не на ИБП** **(владелец)**. Пока это
  так, при пропаже света сеть ложится вместе с ним — СМС «Нет электричества» не уйдёт; на сайте после возврата
  будет «ИБП не отвечает», а затем история перехода на батарею (плата передаст `onbatt_since`). Заработает, когда
  роутер, Wi-Fi и сервер будут запитаны от ИБП (Back-UPS Pro 1200 / BE550G). Сказать об этом в инструкции.

## Анти-цели

- Ложное «нет электричества» (дребезг, короткие провалы, потеря связи с ИБП принята за пропажу света).
- Потерянная СМС «нет электричества» — дубль допустим, потеря нет (как у всех СМС).
- Опрос ИБП тормозит HealthMonitor (недоступный адрес ждёт минутами).
- Поле, которого модель не присылает, показано как 0 или вызывает тревогу (у ES 550 по USB может не быть напряжения
  сети и др.). Нет поля → «нет данных», тревоги по нему не поднимаются.

## Источники данных

У каждого ИБП в настройках — **тип источника** **(моё, согласовано)**:
- **«apcupsd по сети»** — адрес и порт (хост Windows с ВМ, Raspberry Pi рядом с ИБП);
- **«ESP32 по MQTT»** — имя устройства (плата ESP32 у ИБП с COM-портом, первая — котельная).

Дальше всё общее: одно «последнее состояние ИБП» с одинаковыми полями (как в apcupsd), страница, графики, тревоги,
СМС. Новый тип источника потом добавляется без переделки остального.

## Источник «apcupsd по сети» (NIS)

На компьютере, к которому ИБП подключён по USB (хост Windows с ВМ или Raspberry Pi рядом с ИБП), работает apcupsd
с сетевым сервером NIS (TCP, по умолчанию 3551). Протокол: клиент шлёт строку команды с 2-байтной длиной
(big-endian) — `status`; сервер отвечает строками в том же формате, конец — запись нулевой длины. Строки вида
`KEY      : value`.

Используемые поля (если есть): `STATUS` (флаги через пробел: `ONLINE`, `ONBATT`, `LOWBATT`, `REPLACEBATT`,
`OVERLOAD`, `COMMLOST`, `CAL`, `TRIM`, `BOOST`, `SHUTTING DOWN`), `LINEV` (В), `BCHARGE` (%), `TIMELEFT` (мин),
`LOADPCT` (%), `BATTV` (В), `NOMPOWER` (Вт), `LASTXFER`, `NUMXFERS`, `TONBATT` / `CUMONBATT` (с), `XONBATT`,
`SELFTEST` (`OK`, `NO`, `BT` — батарея не прошла, `NG` — перегрузка / сбой), `BATTDATE`, `MODEL`, `SERIALNO`.
Числа идут с единицами («228.0 Volts», «100.0 Percent», «41.5 Minutes») — брать число в начале.

- Опрос каждого ИБП — из HealthMonitor раз в 60 с **(моё)**, все ИБП параллельно, таймаут соединения и чтения 3 с.
- Не ответил 3 опроса подряд, или `STATUS` содержит `COMMLOST` (apcupsd потерял ИБП по USB) → «ИБП не отвечает».
- Последнее состояние каждого ИБП кэшируется в HealthMonitor (как здоровье сервисов) и отдаётся API страницы.

## Источник «ESP32 по MQTT» (котельная)

**Железо** **(моё, согласовано)**: отдельная ESP32 (обычная, не контроллер котельной — контроллер отвечает за защиту
котла, чужой протокол на нём не нужен), модуль RS-232→TTL на MAX3232, кабель к DB9 ИБП с распайкой APC «Smart»
(фирменный кабель 940-0024C: у APC нестандартные контакты — распайку проверить по документации APC до пайки и
записать в `PINOUT.md` прошивки), питание — USB-блок 5 В из розетки самого ИБП (плата работает без света).

**Прошивка** — новый проект `firmware/esp32-ups/` (PlatformIO, как `firmware/esp32-homesite/`; Wi-Fi и MQTT
настраиваются так же, как у контроллера — исполнитель повторяет его способ):
- протокол APC «Smart»: 2400 бод 8N1; `Y` → `SM` (вход в smart-режим); опрос раз в 60 с: `Ctrl-A` модель, `L`
  напряжение сети, `O` напряжение выхода, `f` заряд %, `j` оставшееся время (`0045:` — минуты), `P` нагрузка %,
  `B` напряжение батареи, `Q` флаги (hex: `08` от сети, `10` от батареи, `20` перегрузка, `40` батарея разряжена,
  `80` пора менять батарею), `X` результат самотеста (`OK` / `BT` / `NG` / `NO`), `x` дата замены батареи
  **(моё — коды сверить с документацией протокола APC Smart)**; нет ответа / `NA` — поле отсутствует;
- раз в 60 с публикует одно сообщение `{prefix}{имя}/ups` (JSON, **не retained**): поля в тех же смыслах, что у
  apcupsd (`status` — список флагов `ONLINE` / `ONBATT` / `LOWBATT` / `REPLACEBATT` / `OVERLOAD`, `linev`,
  `bcharge`, `timeleft`, `loadpct`, `battv`, `selftest`, `battdate`, `model`, `uptime`); ИБП не отвечает по COM —
  сообщение с `status: ["COMMLOST"]`;
- при смене режима (сеть ↔ батарея, батарея разряжена) публикует сразу, не дожидаясь минутного цикла **(моё)**;
- сама запоминает момент перехода на батарею и передаёт его (`onbatt_since`, секунды по своему `uptime` — часов
  реального времени у платы может не быть) — если Wi-Fi пропадал, сервер после восстановления связи всё равно
  посчитает «не было N мин» верно **(моё)**;
- ничего не принимает и ничем не управляет (только чтение).

**Шлюз** (`backend/device_gateway/handler.py`): новый подтопик `ups` — хранит последнее сообщение по устройству с
временем получения (как heartbeats) и отдаёт их в своём `/health` (`ups: {имя: {timestamp, data}}`). HealthMonitor
уже читает `/health` каждый опрос — берёт оттуда. «ИБП не отвечает» для ESP32: нет сообщения дольше 3 минут или
`COMMLOST`.

## Настройки

Раздел **«ИБП»** во вкладке «Оборудование» **(моё)**: таблица ИБП (название, модель, что питает, адрес, связь) и
«Добавить». Форма: название (обязательно), модель (список), мощность Вт (только для «Другая»), что питает (текст,
до 200 символов), тип источника; для «apcupsd» — адрес (хост или IP) и порт (по умолчанию 3551), для «ESP32» —
имя MQTT-устройства; включён (галочка — выключенный не опрашивается и не показывает тревог).
«Проверить связь» — для apcupsd разовый опрос, для ESP32 — последнее сообщение от платы и его возраст; показ ответа
(модель, статус, какие поля пришли) прямо в форме. Только admin.

ИБП хранятся в своей таблице (это сущности, как контуры отопления, а не плоские ключи) **(моё)**. Пороги — в
`config_kv` через `setting_rules.py` (admin): `ups_voltage_min` (200 В), `ups_voltage_max` (250 В),
`ups_low_battery_pct` (30 %), `ups_load_max_pct` (90 %) **(моё — значения по умолчанию)**; редактируются в том же
разделе.

## Страница «ИБП»

Пункт меню «ИБП» для всех ролей (смотреть может и viewer) **(моё)**. Карточка на каждый ИБП:
- рисунок, название, модель, «что питает»;
- режим крупно: «От сети» / «От батареи N мин» / «Батарея разряжена» / «Нет связи»;
- заряд %, оставшееся время, нагрузка % и Вт, напряжение сети, напряжение батареи;
- блок «Здоровье»: батарея (норма / пора менять, с номером сменной), последний самотест, дата установки батареи,
  переходов на батарею и сколько всего работал от неё, причина последнего перехода;
- поле, которого нет, — «нет данных».

Ниже — графики за выбранный период (те же варианты, что в «Статистике»): напряжение сети по всем ИБП
(линия на ИБП) с пунктирами порогов, и заряд батарей. Данные графика — из истории (ниже). Обновление страницы — как
у остального сайта (опрос раз в `frontend_poll_seconds`). Мобильный вид — карточки одна под другой, графики во всю
ширину.

## История

Раз в 60 с на каждый ИБП, ответивший в этот опрос, сохраняется строка: ИБП, время (UTC), напряжение сети, заряд,
нагрузка, оставшееся время, напряжение батареи, «от батареи» (bool). Отсутствующее поле — NULL. Хранить 365 дней:
раз в сутки HealthMonitor удаляет строки старше года (только историю ИБП; показания датчиков сейчас не чистятся
вовсе, их не трогаем) **(моё)**. Около 1 440 строк на ИБП в сутки — для SQLite и PostgreSQL это немного. При удалении
ИБП его история удаляется.

## Тревоги

Правила в `alarm_rules.py` (как требует CLAUDE.md), вход — последнее состояние ИБП в `Snapshot`. Коды с id ИБП,
тексты с названием:

| Код | Когда | Уровень | Задержка |
|---|---|---|---|
| `ups_on_battery:{id}` | `ONBATT` | ERROR | 30 с |
| `ups_low_battery:{id}` | `LOWBATT` или заряд < `ups_low_battery_pct` при работе от батареи | ERROR | 0 |
| `ups_voltage:{id}` | напряжение < min или > max при работе от сети (гистерезис 5 В) | WARNING | 120 с |
| `ups_replace_battery:{id}` | `REPLACEBATT` в `STATUS` | WARNING | 0 |
| `ups_selftest:{id}` | `SELFTEST` = `BT` или `NG` | WARNING | 0 |
| `ups_overload:{id}` | `OVERLOAD` или нагрузка > `ups_load_max_pct` | WARNING | 5 мин |
| `ups_unreachable:{id}` | 3 опроса без ответа или `COMMLOST` | WARNING | 0 (счётчик и есть задержка) |

- Тексты: «Нет электричества: «Серверный» работает от батареи, заряд 95%, осталось ~40 мин»; ««Серверный»: батарея
  садится — заряд 25%, осталось ~6 мин»; «Напряжение в сети 190 В («Котельная»)»; ««Серверный»: пора менять
  батарею (APCRBC124)»; ««Серверный»: самотест батареи не прошёл»; ««Серверный»: нагрузка 95% (680 Вт)»;
  «ИБП «Серверный» не отвечает». Формулировки — на исполнителе, смысл и данные — эти.
- Снятие `ups_on_battery`: «Электричество вернулось («Серверный»), не было 12 мин» — как «Интернет есть, не было N
  мин» в `sms_text.summary_text` (длительность от начала эпизода с учётом задержки подъёма).
- Тревоги одного ИБП — отдельные проблемы (без общей `group`): «батарея садится» того же уровня ERROR внутри общей
  группы не считалась бы новостью и не дала бы СМС. Поэтому одна авария даёт «Нет электричества», затем «батарея
  садится», а при возврате — «Электричество вернулось, не было N мин» и «Снято: батарея садится» (склеятся в одну
  СМС) **(моё)**.
- Пока ИБП не отвечает, его тревоги (кроме `ups_unreachable`) удерживаются (механизм `unknown()`), не снимаются.
- Выключенный в настройках или удалённый ИБП — его тревоги снимаются.
- `ups_unreachable` — только баннер, без СМС (добавить в `BANNER_ONLY`-логику по префиксу) **(моё)**.
- Нет поля — правило по нему молчит (без тревоги и без удержания по «нет данных» поля).

## СМС

Через готовую очередь (`SmsNotifier`): склейка нескольких ИБП в одну СМС, «первая сразу — дальше итог, когда
устаканится», тихие часы для WARNING.
- Новая категория получателей **`power`** — галочка «Электричество» в карточке пользователя **(моё, ранее согласовано
  «добавить вместе с ИБП»)**: `ups_on_battery`, `ups_low_battery`, `ups_voltage` идут в неё. «Здоровье»
  (`ups_replace_battery`, `ups_selftest`, `ups_overload`) — по уровню (категория «Предупреждения») **(моё)**.
- Критические тревоги электричества (`ups_on_battery`, `ups_low_battery`, уровень ERROR) получает и тот, у кого
  включены «Аварии», даже без «Электричества» — иначе после обновления никто не узнал бы о пропаже света, пока не
  поставит новую галочку (анти-цель «потеря СМС») **(моё)**. «Электричество» без «Аварий» = только тревоги
  электричества, включая предупреждение о напряжении. Миграция галочек не нужна. Получатель с обеими категориями
  получает одну СМС (это одна проблема).
- Если отправка СМС выключена (`sms_enabled`) — тревоги ИБП видны в баннере, СМС нет (как у всех тревог).

## Имитация

`tools/ups_emulator/` **(моё)**: (1) TCP-сервер с протоколом apcupsd NIS; (2) имитация ИБП с протоколом APC «Smart»
на виртуальном последовательном порту / в тестах прошивки (на исполнителе); (3) имитация платы ESP32 — публикует
`…/ups` в MQTT стенда. Общее для всех: TCP-сервер NIS: несколько ИБП на разных портах,
сценарии (норма; пропал свет — заряд падает; низкое напряжение; пора менять батарею; ES без `LINEV`), смена
сценария без перезапуска (например, по файлу или сигналу — на исполнителе). Используется в тестах и на стенде
(`tools/dev_stack.sh` поднимает имитированные ИБП — два через apcupsd и «котельную» через MQTT — и при первом запуске
добавляет их в базу стенда).

## Инструкция

`docs/ups-apcupsd.md` (по-русски): подключение ИБП USB-кабелем; apcupsd для Windows — установка, `apcupsd.conf`
(`UPSCABLE usb`, `UPSTYPE usb`, `NETSERVER on`, `NISIP 0.0.0.0`, `NISPORT 3551`), правило брандмауэра Windows только
для подсети ВМ; не ставить PowerChute одновременно; второй ИБП на том же хосте — второй экземпляр на другом порту
(**проверить при подключении**, иначе — Raspberry Pi); Raspberry Pi Zero 2 W с apcupsd для ИБП без компьютера рядом;
как проверить связь кнопкой в настройках.

## Проверка

- pytest: разбор ответа NIS (поля с единицами, отсутствующие поля, обрыв, таймаут); правила тревог (каждая строка
  таблицы, гистерезис напряжения, удержание при недоступности, отсутствующее поле молчит); HealthMonitor с имитацией
  (опрос, кэш, история, недоступный адрес не тормозит опрос дольше таймаута); CRUD API ИБП и права; текст «вернулось,
  не было N мин»; категория `power`.
- vitest: страница ИБП (карточки, «нет данных», нет связи), форма в настройках.
- Стенд: два имитированных ИБП, сценарий «пропал свет» → тревога, СМС в журнале, график; скриншоты страницы
  (десктоп + телефон, тёмная тема).
- Прошивка: разбор ответов «Smart» (юнит-тесты на хосте, `pio test -e native`, если в проекте контроллера так
  принято), формирование JSON; на стенде — имитация ESP32 в MQTT → карточка «Котельная».
- После подключения железа (вручную с владельцем): какие поля реально отдают модели, распайка кабеля для Smart-UPS,
  поправить каталог.

## Порядок работы

Сервер с имитацией (оба источника) → прошивка ESP32 на имитации → сборка и проверка в котельной **(моё, согласовано)**.
Ветка — от `main` после слияния ветки СМС **(владелец)**.

## Оставлено исполнителю

Схема таблиц и миграции, имена модулей (предлагаю `app/services/ups_client.py`, `app/services/ups_catalog.py`,
`app/api/v1/ups.py`, `frontend/src/pages/UpsPage.tsx`), вёрстка карточек и рисунки, формулировки текстов, способ
переключения сценариев имитации.
