# СМС-уведомления о тревогах через свой Android-телефон

Дата: 12.11.2026. Решения Andrey помечены **(владелец)**, мои — **(моё)**, их можно оспорить.
Образец — СМС клуба LiteEnglishSite (`LiteEnglishSite/docs/superpowers/specs/2026-11-11-sms-notifications-design.md`):
тот же контракт API для телефона, код пишется заново под FastAPI.

## Зачем

О тревоге в котельной сейчас можно узнать только из баннера на сайте, то есть только если сайт
открыт. Нужна СМС на телефоны домашних: сайт → Android-телефон дома с MacroDroid (по Wi-Fi забирает
очередь) → своя SIM. СМС уходит по сотовой сети, так что сообщение о пропаже интернета тоже
доходит **(владелец)**.

Успех: при аварии СМС приходит через минуту-две. Ночью при дребезге около порога телефон не
звонит пять раз, а приходит одна СМС «упало», потом одна «в норме». Некритичное ночью молчит.

## Цели

- Очередь СМС в бэкенде и API, через которое телефон её забирает (как в клубе).
- Логика «по одной проблеме»: первая СМС сразу, дальше только последнее состояние, когда
  устаканится **(владелец)**.
- Склейка разных тревог, возникших почти одновременно, в одну СМС с ограничением длины **(владелец)**.
- Журнал СМС **(владелец)**.
- Получатели и что им слать — в карточке пользователя **(владелец)**.
- Новый источник тревоги: пропал интернет (критическая) **(владелец)**.

## Не цели

- Электричество / ИБП APC (подключён по сети) — остаётся в TODO **(владелец)**. Очередь и правила
  устроены так, чтобы оно добавлялось как ещё одна тревога.
- Советы по эффективности (уровень INFO) по СМС не идут.
- Отчёты о доставке от оператора, входящие СМС, ответы.
- Мобильное приложение: поля телефона и галочки СМС в его админке не делаем **(моё)**.
- iPhone как отправитель.

## Анти-цели (провал, даже если «работает»)

- Потерянная аварийная СМС. Дубль допустим, потеря — нет.
- Поток СМС при дребезге одной тревоги.
- Лавина СМС после перезапуска бэкенда (тревоги в `AlarmTracker` живут в памяти и после рестарта
  поднимаются заново — это не новость).
- Некритичная СМС ночью.
- Ключ API в адресе запроса или открытым текстом в базе.

## Уровни и тихие часы

| Что | Когда уходит |
|---|---|
| Тревога `ERROR` (критическая), в том числе «нет интернета» **(владелец)** | сразу, круглосуточно |
| Снятие критической тревоги | сразу, круглосуточно **(владелец)** (после «устаканилось», см. ниже) |
| Тревога `WARNING` и её снятие | вне тихих часов **(владелец)**; накопленное за ночь — после их конца |
| `INFO` / советы | никогда |

Тихие часы — настройка, по умолчанию 22:00–08:00 по времени дома **(моё)**. Хранятся в `config_kv`
в UTC, как `backup_time`; интерфейс показывает и принимает местное время **(моё)**.

## Логика по одной проблеме

«Проблема» — тревога с её `group`, если он есть, иначе с её `code` **(моё)**: тревоги одной группы
(предупреждение → авария по тому же датчику) — это одна проблема, меняется её уровень.

У проблемы для каждого получателя есть **последнее отправленное состояние** (нет / поднята с
уровнем L / снята). Оно хранится в базе по паре (проблема, получатель) **(моё)**: получатели
фильтруют по категориям, и у каждого своя история — тот, у кого включены только аварии, не
получит «снята» по предупреждению, о котором ему не писали, а при ухудшении до `ERROR` получит
обычную первую СМС «поднята». Получатель, добавленный посреди эпизода, начинает с «нет». Хранение
в базе нужно и для того, чтобы рестарт бэкенда не порождал повторных СМС.

**Изменением считается только состояние**: поднята / снята / сменился уровень **(моё)**. Значение
в тексте (давление, температура) меняется каждый опрос — это не изменение; текст СМС берётся
актуальным на момент её формирования.

1. **Первая СМС — сразу.** Проблема поднялась (после задержки, которая уже есть в правилах тревог),
   а последнее отправленное — «нет» или «снята» → СМС «поднята» ставится в очередь сразу (с учётом
   окна склейки и тихих часов для `WARNING`).
2. **Дальше — только последнее состояние, когда устаканится** **(владелец)**. Любое изменение после
   первой СМС (снялась, поднялась снова, текст/значение поменялось) создаёт новую СМС «итог»
   с моментом отправки «последнее изменение + время успокоения» (настройка, по умолчанию 10 мин
   **(моё)**). Каждое следующее изменение заменяет неотправленную СМС этой проблемы: старая
   получает в журнале статус «заменена», срок сдвигается.
3. **Итог совпал с отправленным** («упало» → поскакало → снова «упало») — СМС не нужна, в журнале
   статус «не нужна» **(моё, согласовано)**.
4. **Текст итога** — текущее состояние и, если было больше одного изменения, сколько раз
   переключалось: «Давление в норме: 1.4 бар (за 40 мин 5 раз туда-обратно)» **(моё)**.
5. **Ухудшение уровня** (`WARNING` → `ERROR`) — новость: уходит сразу, как первая СМС
   **(моё, согласовано)**.
6. **Конец эпизода.** После того как ушёл (или признан ненужным) итог «снята», следующий подъём —
   снова «первая СМС, сразу».
7. **Тихие часы для итога** следуют за последним отправленным получателю уровнем **(моё)**: кому
   ушла авария (`ERROR`), тому итог — снятие или снижение до `WARNING` — уходит сразу и ночью
   (это восстановление после критической **(владелец)**); кому ушло только предупреждение — итог
   ждёт утра. Снижение `ERROR` → `WARNING` внутри группы трекер даёт как «новая поднята + старая
   снята» в одном обновлении — для СМС это одно изменение уровня проблемы.
   **Тихие часы и `WARNING`.** Срок СМС не раньше конца тихих часов. Если предупреждение поднялось
   и снялось ночью, утром итог «снята» совпадает с отправленным «нет» → ничего не уходит.
8. **После перезапуска бэкенда** тревога, поднявшаяся заново с тем же уровнем, что записан как
   отправленный, СМС не даёт. Проблемы, записанные как «поднята», которых после старта нет среди
   активных дольше максимальной задержки подъёма + время успокоения, считаются снятыми → итог
   «снята» **(моё)**.

## Склейка

- Разные проблемы для одного номера, чьи СМС готовы к отправке одновременно, уходят одной СМС
  **(владелец)**. Новая «первая СМС» ждёт короткое окно склейки (настройка, по умолчанию 60 с
  **(моё)**), чтобы собрать то, что сработало вместе (часто одна причина).
- Склейка делается при выдаче телефону: все готовые записи для номера → одна СМС.
- **Ограничение длины** **(владелец)**: не больше 2 частей — 134 символа кириллицей. Порядок:
  `ERROR` раньше `WARNING`, поднятые раньше снятых; не влезающее — «…и ещё N, подробнее на сайте»
  **(моё, как в клубе)**. Одна тревога длиннее лимита обрезается с «…».
- В журнале видно, какие записи вошли в склеенную СМС и сколько их.
- **Сформированная СМС неизменна** **(моё)**: повтор после неудачи шлёт тот же текст, даже если
  по одной из проблем уже готов более свежий итог — он уйдёт следующей СМС (дубль допустим, потеря
  нет). Итог, появившийся, пока предыдущая СМС проблемы выдана телефону, не отменяет её: уходят обе.
  Значит, склеенная СМС — отдельная сущность (своя строка с текстом, номером, статусом и попытками),
  а записи очереди на неё ссылаются.
- Заменять (статус «заменена») можно только записи, ещё не вошедшие в сформированную СМС.

## Получатели

В карточке пользователя (раздел пользователей в «Настройках») **(владелец)**:
- телефон (нормализуется к `+7…`) и галочки: аварии (`ERROR`), предупреждения (`WARNING`), связь с
  контроллером, интернет, тестовые СМС **(моё, согласовано)**. Галочку «электричество» добавить
  вместе с ИБП. По умолчанию всё выключено.
- Менять телефон и галочки может только admin **(моё, согласовано)** — иначе можно подставить свой
  номер в чужую учётку.
- Получать может любой активный пользователь с номером, роль не важна **(моё, согласовано)**.
- Без номера или неактивный — пропускается. Одинаковый номер у двух пользователей — одна СМС.
- Категория тревоги: «связь с контроллером» и «интернет» определяются по коду/группе тревоги,
  остальное — по уровню **(моё)**. Если у пользователя включена категория «связь» и выключены
  «аварии», он получает только связь. «Связь» — группа `link` (`svc:gateway`, `svc:mqtt`, `no_link`).
- Тревоги только для баннера (телефон СМС молчит, СМС не отправлены, нет локальной сети, проверка
  аварий не работает) исключаются из СМС по коду **(моё)**. Квитирование тревоги на сайте на СМС
  не влияет **(моё)**.

## Пропал интернет

- HealthMonitor раз в минуту **(моё)** пытается открыть TCP-соединение с несколькими адресами
  из разных сетей, российскими и зарубежными (список — настройка, по умолчанию, например,
  `77.88.8.8:53`, `1.1.1.1:53`, `ya.ru:443`, `8.8.8.8:53`) **(моё)**.
- Все недоступны 5 мин подряд (настройка) → тревога `internet_down`, уровень `ERROR` **(владелец:
  критическая)**. Часть недоступна — не авария.
- Если недоступен сам роутер (адрес — настройка, по умолчанию шлюз ВМ), «нет интернета» не
  поднимается: до телефона тоже не достучаться. Вместо неё — тревога «нет локальной сети» только в
  баннере и журнале событий, без СМС **(моё)**.
- Снятие: «Интернет есть, не было 47 мин» — по общей логике (итог после успокоения, сразу ночью).
- Проверка — вход для правил тревог (результат пробы в `Snapshot`), сама тревога — правило в
  `alarm_rules.py` с тестом, как требует CLAUDE.md.

## Очередь

Состав таблиц — на исполнителе. Нужно хранить:
- запись очереди: проблема, тип/код тревоги, уровень, получатель (пользователь и номер на момент
  создания), текст, статус, `created_at`, `ready_at`, `leased_until`, попытки, ошибка, `sent_at`,
  признак тестовой, связь со склеенной СМС (какие записи ушли вместе и её итоговый текст);
- состояние проблемы: последнее отправленное, число изменений с него, время последнего изменения.

Статусы в журнале: ждёт / выдана телефону / ушла / не ушла / заменена / не нужна.

- Выдача: самая старая готовая запись (`ready_at` наступил) или выданная с истёкшей бронью.
  Бронь 10 мин. Захват атомарный (`UPDATE … WHERE state = … ` + проверка `rowcount`) — один процесс
  uvicorn, но HealthMonitor пишет в ту же таблицу.
- `ok: false` → обратно в очередь с паузой 5, 15, 60 мин; после 3 неудач — «не ушла» и тревога
  `WARNING` «N СМС не отправлено» в баннере (сама по СМС не шлётся) **(моё, как в клубе)**.
- Аварийные СМС выдаются и после долгого молчания телефона — лучше поздно; устаревшее и так
  заменяется итогом.
- Записи старше 90 дней удаляются (раз в сутки из HealthMonitor) **(моё)**.

## API для телефона

Как в клубе, база `/api/v1/sms/`, JSON UTF-8:

| Метод | Ответ |
|---|---|
| `GET ping` | 200 `{"mode":"live","queue":3,"quiet":false,"poll_after":60}` |
| `GET next` | 200 `{"id":17,"to":"+79001234567","text":"…","poll_after":60}`; 204 — пусто (`X-Poll-After` в заголовке) |
| `POST done` `{"id":17,"ok":true}` / `{"id":17,"ok":false,"error":"нет сети"}` | 200 `{"ok":true,"poll_after":60}`; 404 — нет такого id для этого ключа; повтор — 200 |

- Ключ: `Authorization: Bearer <ключ>` или `X-SMS-Key`; в адресе не принимается. Два ключа —
  боевой и тестовый (тестовый видит только тестовые записи). Создаются кнопкой в разделе СМС
  (admin), показываются один раз, в `config_kv` — SHA-256; сравнение `hmac.compare_digest`.
  Ключи не проходят через `PUT /settings`.
- Неверный ключ — 401; лимит 60 запросов/мин на IP через SlowAPI — 429.
- `poll_after` один для дня и ночи, 60 с (настройка) **(моё)**: аварии идут и ночью, а интервал
  MacroDroid — минута.
- Боевой запрос обновляет «последний опрос телефона».
- Телефон молчит дольше `max(15 мин, 3 × poll_after)` при наличии боевого ключа и хотя бы одного
  получателя → тревога `ERROR` «Телефон СМС не на связи» в баннере, без СМС **(моё, согласовано)**.
- Swagger: встроенный FastAPI `/docs` на тестовом ключе. Инструкция для MacroDroid (интервал 1 мин,
  цикл next → отправить → done → next до 204, отключить оптимизацию батареи) — в разделе СМС.

**HTTPS.** Nginx на проде — самоподписанный сертификат. Первым делом проверить, принимает ли его
MacroDroid; если нет — отдельный HTTP-порт Nginx только для `/api/v1/sms/` и только из LAN
(телефон дома в Wi-Fi) **(моё)**.

## Раздел «СМС» (admin)

- Журнал **(владелец)**: свежие сверху, по 50 на страницу. Колонки: создана, тип (тревога/событие),
  текст, кому (имя и номер), статус, склеено (сколько и каких), попытки и ошибка, ушла.
  Фильтры: статус, тип, получатель, тестовые/боевые (по умолчанию боевые). «Повторить» у «не ушла».
  Без правки и удаления.
- Над журналом: последний опрос телефона, сколько ждёт и не ушло.
- Настройки: тихие часы, окно склейки, время успокоения, `poll_after`, интернет (адреса, минуты,
  роутер). Все ключи — в `setting_rules.py`, admin-only.
- Ключи: создать / перевыпустить боевой и тестовый.
- Кнопки «Отправить мне тестовую СМС» (боевая очередь, на свой номер) и «Создать тестовую СМС»
  (тестовая очередь, для Swagger).

## Проверка

- pytest на логику проблемы с подменными часами: первая сразу; дребезг → одна итоговая; итог
  совпал → «не нужна»; ухудшение сразу; `WARNING` ночью ждёт утра, поднялось и снялось ночью →
  ничего; снятие `ERROR` ночью уходит; рестарт (новый трекер, то же состояние в базе) → ни одной СМС;
  тревога исчезла за время простоя → итог «снята».
- Склейка: порядок, лимит 134, «…и ещё N», одна длинная.
- Получатели: галочки по категориям, без номера, неактивный, общий номер.
- API: бронь и повтор через 10 мин, 3 неудачи → «не ушла» + тревога, тест/боевой, 401/429, 204 +
  `X-Poll-After`, ключ в query не принимается, молчание телефона → тревога.
- Интернет: правило тревоги (все недоступны N мин; часть; нет роутера).
- Вручную: стенд (`tools/dev_stack.sh`) + Swagger на тестовом ключе, затем настоящий телефон.
